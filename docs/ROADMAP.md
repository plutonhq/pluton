# Fork roadmap

This public Apache-2.0 fork plans independently developed backup-management
capabilities for existing Restic environments. Use only the open-source Pluton
codebase, public Restic/Rclone interfaces, and independently written code. Preserve
upstream attribution and the Pluton name; proprietary PRO/Business implementations
and binaries are outside the development inputs.

Phases 0-2 are complete within the stated local, read-only boundary. Phases
3-6 retain their original planned descriptions here; separate phase documents record
their scoped implementation. Phase 7 is locally implemented as documented below.
The [architecture baseline](ARCHITECTURE.md) distinguishes
managed community functionality from the separate legacy adapter.

| Phase                                                     | Planned scope                                                                                                                                                                                                                                                          | Completion evidence                                                                                                                                                                                                                                                         |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0 — Repository preparation                                | Complete: agent instructions, public-repository hygiene, architecture documentation, and an existing Restic compatibility analysis. No production access or live compatibility certification occurred.                                                                 | Guardrails/design were reviewed, licenses and environment templates preserved, ignore rules checked, and validation commands recorded.                                                                                                                                      |
| 1 — Legacy Restic Repository Adapter                      | Complete for local filesystem repositories: register an existing repository separately from managed plans, encrypt its independent password locally, enforce read-only access, list snapshots, inspect safe metadata/statistics, and filter by exact path/tag/host.    | Dedicated allowlisted inspector uses `--no-lock`, argument arrays, structured JSON, bounded output, sanitized errors, and tests that deny all eight repository-mutating commands. Mocked generic fixtures were used; compatibility with a live repository is not certified. |
| 2 — Snapshot Browser and granular restore                 | Complete for local legacy repositories: browse structured snapshot entries and restore selected files/directories only into an app-controlled isolated staging workspace.                                                                                              | Typed `ls --json` parsing, strict logical-path validation, job persistence, containment checks, safe single-file downloads, cancellation, migration tests, and disposable Restic Docker validation preserve repository-read/staging-write behavior.                         |
| 3 — Pilot migration of one backup workload                | Separately authorize and document a controlled pilot for one synthetic/example workload, such as `app-01` and `/srv/example-app`, before applying the procedure privately to a real workload. Define validation, rollback, scheduling ownership, and cutover criteria. | Recovery from a staged restore is verified; the existing legacy repository remains read-only. Any new managed writes use a separately approved destination. No automatic repository conversion or retention takeover.                                                       |
| 4 — Remote Machine / independently developed Agent        | Design and implement remote execution, authentication, capability boundaries, and lifecycle using independently written code and public interfaces.                                                                                                                    | Protocol/security review and tests for identity, authorization, disconnection, upgrades, cancellation, and scoped filesystem access. Existing public strategy hooks are not a completed agent.                                                                              |
| 5 — Pre/Post Backup Scripts and database backup lifecycle | Assess existing community script hooks, then define the additional database dump/consistency, timeout, failure, artifact handling, and cleanup lifecycle.                                                                                                              | Tests establish execution order, failed-dump behavior, credential redaction, and safe cleanup of generic database fixtures. No production credentials in examples.                                                                                                          |
| 6 — Automated Recovery Testing                            | Restore into isolated disposable staging environments, validate recovery results, and report failures with bounded resource use and safe cleanup.                                                                                                                      | Repeatable recovery checks cannot overwrite live data or mutate imported repositories. Tests cover partial restores and failed cleanup.                                                                                                                                     |
| 7 — Webhook and email notifications                       | Complete locally: outgoing webhook/SMTP channels, opt-in per-plan terminal events, durable leased outbox, bounded retry, sanitized history, test delivery and management UI.                                                                                           | [Phase 7 evidence and acceptance](PHASE7_WEBHOOK_NOTIFICATIONS.md): isolated receivers, HMAC/DNS/TLS/security tests and existing workflow regressions. No production deployment or acceptance is claimed; community notifications remain attributed as existing.            |

Each later phase needs a scoped implementation task and backend tests for new behavior.
Do not enable later phases as part of Phases 1-2. Registration never implies
permission to assume ownership of an existing repository's retention or maintenance.

The next task, if separately authorized, may assess Phase 3 pilot migration using
only a synthetic/example workload. Remote agents, database lifecycle, recovery
testing, and notification extensions remain later work.
